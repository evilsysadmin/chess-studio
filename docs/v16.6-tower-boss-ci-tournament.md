# V16.6 — La Torre, Rey Boss, torneo y CI

## Roguelike: objetivo de la Torre

La Torre principal dura **10 pisos**. Los encuentros se derivan de `seed + floor`, por lo que recargar la UI no vuelve a tirar el modificador. Hay encuentros normales, élites, miniboss y un jefe final. Entre pisos superados se elige una recompensa temporal de entre tres opciones deterministas.

Las recompensas modifican Fuerza o Velocidad durante **ese intento**. No se guardan en el roster permanente y desaparecen al terminarlo. La veteranía/XP real del ejército de Combate mantiene su metaprogresión normal.

La máquina de estados sigue siendo estricta: `battle -> fighting -> cleared -> recompensa -> siguiente piso`. En piso 10 una victoria cambia a `completed`; desde ahí se puede cerrar el intento victorioso o continuar al piso 11 en modo infinito.

## Rey Boss: experimento de HP controlado

HP sólo existe de momento para el **Rey Viejo** del piso 10. Ninguna otra pieza usa barras de vida.

- HP inicial: **5**.
- Jaque humano válido: **-1 HP**.
- Jaque mate humano: **-2 HP**.
- 3–2 HP: fase II.
- 1 HP: fase III.
- 0 HP: boss derrotado y Torre completada.

Un mate que no agota los HP no se convierte en una falsa captura del rey. El boss rompe la posición y abre una fase nueva de forma explícita. El ejército del jefe se recompone, pero **las bajas humanas no resucitan** y las supervivientes arrastran sus stats/XP de la pelea. Es una primera versión deliberadamente conservadora para comprobar si HP añade diversión sin desfigurar el ajedrez.

## Torneo: tres señales distintas

V16.5 reutilizaba `points` como moneda para pistas **y** XP de nivel. Eso tenía dos efectos indeseables: capturar piezas podía endurecer el rival sin haber ganado partidas, y gastar una pista podía reducir el nivel. V16.6 separa responsabilidades:

- `points`: moneda disponible para pistas. Las capturas sólo suman aquí.
- `progressPoints`: XP de torneo; sólo los resultados de partida lo incrementan.
- Rating ELO: sólo cambia una vez al terminar la partida mediante `updateRating(...)`. Victoria=1, tablas=0.5, derrota/abandono=0.
  La magnitud del cambio es dinámica: compara el rating del jugador con un rating efectivo interno de la CPU derivado por tramos de dificultad. La pantalla de Torneo muestra el delta y la fuerza efectiva usada.

Los perfiles antiguos migran una vez copiando el antiguo `points` a `progressPoints`, para no borrar de golpe el nivel histórico. Desde esa migración ambas cifras divergen correctamente.

La curva del torneo también se recalibra a `10 * sqrt(level-1)`. El motor actual es más fuerte que cuando se definió la curva vieja: por ejemplo, alrededor del nivel 24 la CPU queda en ~48 en lugar del antiguo ~62.

## Movimiento ilegal y seguridad del rey

En intentos claros de mover una pieza absolutamente clavada (o el rey a una casilla adyacente ilegal por seguridad), suena un beep doble. La CPU añade al Game Chat una explicación una sola vez por partida; los beeps pueden repetirse si el usuario insiste, pero el chat no se llena de la misma frase.

## Última actividad

Cada request autenticada/heartbeat mantiene `last_activity` con throttling. Los accesos forzados de login guardan también `last_login`. El panel admin usa `last_activity -> last_login -> created_at` como fallback para cuentas legacy, de forma que un documento antiguo no aparezca como “Sin actividad” por falta del campo nuevo.

## CI / GitHub Pages

`.github/workflows/static.yml` ejecuta:

1. `npm ci` — **sólo instala** exactamente el lockfile.
2. Gate crítico de Vitest (Combate/Roguelike, legalidad, voz, rating, torneo, auth y sonido).
3. Suite frontend completa con `npm test`.
4. `npm run build`.
5. Deploy a GitHub Pages sólo si todo lo anterior pasa.

`ci.yml` sigue ejecutando backend + frontend en push/PR.
